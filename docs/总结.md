## 一、一句话介绍

**UCT8086-AI（Open Agent Harness）** 是一个基于 **Java 21 + Spring Boot 4.0 + Spring AI 2.0** 构建的 **AI Agent 工程化基础设施**，对标港大开源项目 [HKUDS/OpenHarness](https://github.com/HKUDS/OpenHarness)，提供从「模型调用 → 工具执行 → 权限管控 → 会话/记忆/成本管理 → 多租户与可观测」的完整 Agent 闭环能力。

它不是「套壳一个 Chat 接口」，而是一套可插拔的 **Agent 运行时框架**：内置 Agent Loop、Tool Registry、Hook 生命周期、四级权限模式、RAG 向量检索、记忆自动固化、成本熔断、MCP 协议接入、SSE 流式输出与 Prometheus 指标。

### 3.2 Agent Loop 核心流程

```
用户 Prompt
   │
   ├─ 1. 成本熔断检查（assertQuota，超限直接拒绝）
   │
   ├─ 2. 创建/恢复会话（MySQL + Redis 缓存）
   │
   ├─ 3. 组装 System Prompt（PromptAssembler）
   │      ├─ 注入系统技能 + 用户技能（每条截断到 4000 字符）
   │      ├─ 注入相关记忆（向量检索，最多 5 条）
   │      └─ RAG 检索知识库文档（topK=3，与 memory 类型隔离）
   │
   ├─ 4. 加载历史消息（截取最近 N 条）
   │
   ├─ 5. 构建 ToolCallback（内置工具 + 用户 MCP 工具）
   │
   ├─ 6. ChatClient + HarnessToolCallingAdvisor 循环
   │      （模型请求工具 → 执行管线 → 结果回传 → 直到无工具调用）
   │
   └─ 7. 持久化消息 + 记账（cost_usage）+ 记录指标
```

### 3.2.1 ChatClient / Advisor / Agent Loop 机制深挖（Spring AI 2.0）

> 面试能体现「不只是会用框架，还懂内部原理」的一节。

**① ChatClient 是「流式 Builder 门面」**，不是对模型的直接封装。三层语义：

```java
ChatClient chatClient = ChatClient.builder(chatModel)   // 指定底层 ChatModel
        .defaultSystem(systemPrompt)                     // 默认值：每次调用都带
        .defaultOptions(optionsBuilder)                  // 工具回调 + model + temperature
        .defaultAdvisors(harnessAdvisor)                 // 拦截器链
        .build();

chatClient.prompt().messages(history).user(userPrompt)   // 单次请求（覆盖/追加默认值）
        .call() / .stream()                              // 触发执行
```

`defaultXxx` 是「公共底座」，`prompt()` 是「单次增量」——`build()` 一次可反复 `.prompt()` 发不同消息。

**② Advisor = 责任链拦截器**（ChatClient 的核心扩展点）。`HarnessToolCallingAdvisor` 继承 `ToolCallingAdvisor`，重写 4 个生命周期钩子：

| 钩子 | 触发时机 | 本项目用途 |
|------|---------|-----------|
| `doInitializeLoop` | Agent Loop 开始前（仅一次） | 初始化 toolCallRecords 列表 + turns 计数器 |
| `doBeforeCall` | 每次调模型前 | `turns++` |
| `doAfterCall` | 每次模型返回后 | 若有 tool call，记录 name/arguments |
| `doFinalizeLoop` | 循环结束后 | 把收集数据放进 `ChatClientResponse.context()` 回传 |

这解释了为什么主循环能拿到 `turns`/`toolCallRecords`——**不是模型返回的，是 Advisor 在循环中拦截收集、塞进 response context 带出的**。

**③ Agent Loop 的真相：`ToolCallingAdvisor` 内部的「隐式 while 循环」**。代码里看到的「一次 `.call()`」，底层可能调了模型 N 次：

```
call() → 模型返回 tool_calls
        → ToolCallingManager 执行工具
        → "tool_call + tool result" 追加进消息历史（conversationHistoryEnabled=true）
        → 再 call() → 模型看到结果继续推理
        → ... 直到模型返回「无 tool_calls 的纯文本」
```

三个关键结论：
- 一次 `.call()` 内部可能调模型多轮，所以 `turns` 能 > 1。
- `conversationHistoryEnabled=true`（`AgentEngine.java:365` 传入）让 Advisor 自动追加工具调用历史，否则模型「失忆」。
- `maxTurns`（默认 20）是隐式循环上限，防止模型无限调工具烧钱。

**④ 底层落地：ChatModel + OpenAI 协议适配**。`ChatModel` 是统一抽象，把 `Prompt`（含工具 schema）序列化成 OpenAI `tools` JSON 发给 `base-url`（DeepSeek，**必须含 `/v1`**），再解析回 `ChatResponse`。工具能工作，正是因为 `ToolCallback` 被序列化成了 OpenAI 的 `tools` JSON schema 告诉模型「我能调什么、参数长啥样」。

**⑤ 全景图**：

```
ChatClient.prompt().call()
   →【Advisor 链】doInitializeLoop（初始化计数器）
   →【隐式循环】doBeforeCall → ChatModel.call()
                    ├─ 返回 tool_calls? 是 → ToolCallingManager 执行工具 → 结果入历史 → 循环
                    └─ 否 → 结束
   → doAfterCall / doFinalizeLoop → ChatClientResponse（含 context 里的 turns/toolCallRecords）
```

### 3.3 工具执行管线（每次工具调用必经）

```
ToolExecutionService
   1. Permission Check   ← 权限模式 + 路径规则 + 危险命令拦截
   2. PreToolUse Hook    ← 可阻止执行
   3. Execute Tool       ← 实际执行逻辑
   4. PostToolUse Hook   ← 可修改结果
```

## 四、核心子系统详解

### 4.1 认证与多租户（本次升级重点）

- **认证方式**：Spring Security + 无状态（`SessionCreationPolicy.STATELESS`）。
- **Token 设计**：**Redis opaque token**（随机 UUID），而非 JWT。理由：天然支持即时吊销（logout 直接删 key）、跨节点无状态、实现简单。
  - 存储：`auth:token:<uuid>` → 用户身份 JSON，TTL 24h。
  - 流程：`AuthController` 登录 → BCrypt 校验 → `AuthTokenService.issueToken` → 写入 `auth_token` Cookie → `AuthTokenFilter` 每次请求解析 Cookie 还原 principal。
- **RBAC**：`auth_user` / `auth_role` / `auth_user_role` 三表，默认角色 `ROLE_USER` / `ROLE_ADMIN`，默认管理员 `admin/admin123`。
- **多租户隔离**：**全链路 `userId` 维度**贯穿所有数据访问。
  - MySQL：每张业务表（session/message/memory/cost/skill）都带 `user_id` 列 + 索引，所有 Mapper 查询按 `userId` 过滤。
  - Redis：所有 key 命名空间化，如 `harness:session:zset:{userId}`、`harness:session:messages:{userId}:{id}`，杜绝跨用户缓存泄漏。
  - 向量：记忆文档 metadata 携带 `userId`，检索后代码层过滤。
  - MCP：每个用户独立维护自己的连接集合（`Map<Long, List<McpSyncClient>>`）。

### 4.2 会话管理（SessionManager）

- **持久化**：MySQL `harness_session` + `harness_message`（MyBatis-Plus）。
- **缓存**：三级 Redis 缓存，全部按 `userId` 隔离：
  - `harness:session:zset:{userId}`：ZSET 有序索引（score = updatedAt），支持分页列表。
  - `harness:session:meta:{userId}:{id}`：单会话元信息 JSON（TTL 10m）。
  - `harness:session:messages:{userId}:{id}`：消息列表 JSON（TTL 10m）。
- **缓存策略**：新增消息时**追加更新**（而非整体失效），因单用户单会话写串行，无并发读改写竞态；Redis 不可用时自动降级 DB 分页查询。
- **关键修复**：会话命名从 `session-<count>`（全表 count + 并发重名）改为 **UUID**，消除竞态。

### 4.3 成本追踪与熔断（CostTracker）

- **持久化**：成本明细写入 MySQL `cost_usage` 表（而非内存累加器），`getSessionUsage`/`getTotalUsage` 用 SQL `SUM` 聚合。好处：重启不丢、多实例共享、可追溯。
- **定价**：输入/输出价格可配置（`input-price-per-m` / `output-price-per-m`），默认 DeepSeek 定价，按 1M token 计价。
- **熔断机制（Circuit Breaker）**：
  - 请求前 `assertQuota`：用户总成本 ≥ 硬上限 → 抛 `CostLimitExceededException` 拒绝请求。
  - 熔断标志存 Redis `harness:cost:breaker:{userId}`，TTL 24h。
  - 多级告警：会话级 WARN/硬限、用户总成本 WARN/硬限，通过 Spring `ApplicationEventPublisher` + 自定义监听器触发。
- **价值**：防止单用户或整体 API 费用失控，把「成本控制」变成系统级能力而非事后统计。

### 4.4 RAG 与记忆向量化（同一向量库的巧妙复用）

- **Embedding**：本地 Ollama `bge-m3`（1024 维），免费、数据不出内网。
- **向量库**：Spring AI 原生 `PgVectorStore`，手动配置独立 PostgreSQL 数据源（`PgVectorConfig`），**排除自动配置**避免冲突，`@Qualifier("pgVectorStore")` 注入。
- **为什么不用 DeepSeek 做 Embedding**：DeepSeek 无 Embedding API，Ollama 本地补位。
- **知识库 vs 记忆 的隔离（设计亮点）**：
  - 知识库文档和记忆共用**同一个** `PgVectorStore`。
  - 靠 metadata `type` 字段区分：记忆文档 `type=memory`，知识库文档无此标记。
  - `MemoryVectorService.search` 检索后**代码层过滤** `type=memory` + `userId`（而非依赖数据库 filter 表达式，避免 provider 差异）。
  - `AgentEngine.enrichWithRag` 检索知识库时**排除** `type=memory` 文档。
  - 这样记忆和知识库各自独立检索、互不污染，但只维护一套向量基础设施。
- **RAG 注入**：每次 Agent 调用前 `similaritySearch(topK=10)` → 排除 memory → 取 3 条拼到 System Prompt。
- **记忆注入**：按相关性检索（最多 5 条）而非全量注入，控制 prompt token 预算。
- **元数据类型陷阱（已解决）**：PgVectorStore 读回数字 metadata 可能是 Integer/String 而非 Long，`Long.equals()` 会静默失败，故 `userId` 比较统一转 `String.valueOf`。

### 4.5 记忆自动固化（MemoryConsolidationService）

- **机制**：定时任务（cron，默认每小时）扫描所有启用用户，读取「上次水位线之后」的新消息，**调用模型**提取用户的稳定偏好/事实（如技术栈偏好、沟通习惯、项目背景），写入记忆库。
- **增量 + 幂等**：水位线存 Redis `harness:memory:watermark:{userId}`，每次处理推进，跨实例共享、可恢复。
- **提取约束**：Prompt 明确「只提取长期有用的事实/偏好，不提取对话过程」，输出严格 JSON 数组，代码 `extractJson` 剥离 markdown 代码围栏。
- **价值**：把「跨会话记忆」从手动维护变成自动化，且保证记忆库高信噪比。

### 4.6 技能系统（SkillRegistry）

- **来源**：系统技能（代码目录）+ 用户技能（MySQL `harness_skill` 表，按用户隔离）。
- **注入**：`AgentEngine.buildSystemPrompt` 把系统技能和用户技能都注入，每条技能内容截断到 4000 字符，控制 prompt 预算。

### 4.7 MCP 客户端（Model Context Protocol）

- **自实现 MCP client**：`uct8086.ai.client.McpClient`（含 `McpSyncClient`，SyncSpec 用反射实例化底层 `McpAsyncClient`），基于 `HttpClientStreamableHttpTransport`。
- **按用户多连接管理**：`McpConnectionManager` 用 `ConcurrentHashMap<Long, List<McpSyncClient>>` 维护每个用户的连接集合，懒连接（首次访问或显式 refresh 时建立）。
- **超时保护**：MCP 工具调用设显式超时（`mcpRequestTimeoutSeconds`，默认 30s），慢 MCP 服务器不会无限拖住 Agent Loop。
- **工具集成**：MCP 工具通过 `SyncMcpToolCallbackProvider` 转成 Spring AI `ToolCallback`，与内置工具统一注入。

### 4.10 为什么自研，不用 LangChain / 阿里 AgentScope？（2026-08-16）

> 面试高频追问：「你这个和 LangChain / AgentScope 有什么区别，为什么不直接用那些框架？」

**一句话定位**：LangChain / AgentScope 是**编排框架**，回答「Agent 怎么写」（把 LLM、工具、记忆快速串成链路）；UCT8086-AI 是 **Agent 运行时基础设施**，回答「Agent 怎么跑、怎么管、怎么不失控」。两者不在同一层，是互补而非替代。

**三个维度拆解**：

**① 关注点不同：写 Agent vs 运维 Agent**

| 维度 | LangChain / AgentScope | UCT8086-AI |
|------|----------------------|------------|
| 核心价值 | 降低「构建一个 Agent」的门槛（链、工具抽象、Prompt 模板） | 降低「把 Agent 跑进生产」的门槛 |
| 典型问题 | "这条 RAG 链怎么快速搭起来" | "用户打光 4 万 token 怎么熔断？子代理会话怎么隔离？怎么审计某次工具调用" |
| 交付物 | 应用代码、Chain/Graph 对象 | 运行时框架、REST/SSE 服务、持久化、指标 |

**② 工程化能力是框架的盲区**（真正差异化所在，框架默认不给、需自己拼中间件）：

- **权限与安全**：四级权限模式 + 危险命令拦截 + 路径规则 + 工具执行管线 Hook（框架里要自己接 sandbox）
- **成本控制**：SQL 聚合成本明细 + 请求前熔断 + 多级告警（框架里 token 是纯消费，无预算闭环）
- **多租户**：全链路 `userId` 隔离（MySQL 表 / Redis key / 向量 metadata / MCP 连接）（框架默认单机单用户）
- **记忆与 RAG 持久化闭环**：记忆自动固化 + 向量检索 + 知识库/记忆 type 隔离（不是给个 VectorStore 接口，而是自动化跨会话记忆）
- **协议接入（MCP）**：按用户多连接管理 + 超时保护，接入外部工具生态

> 用 LangChain 一个下午能搭出 Agent demo，但要变成「多用户、带权限、带成本、能审计、能监控」的服务，这部分工作一点不会少，且恰好是框架帮不上忙的地方——我做的就是把它们做成基础设施。

**③ 技术栈绑定 + 掌控力**：

- **生态绑定风险**：LangChain 抽象层厚、版本迭代快、黑盒多；AgentScope 深度绑定阿里模型/云生态。用它们出了问题难定位到「哪一层」。
- **选 Spring AI 而非 LangChain4j/LangChain**：Spring AI 是**轻量抽象**（贴近 Spring Boot 4.0 + Java 21），只抽象 ChatClient/ToolCalling/VectorStore 接口；**执行循环、权限、成本等核心逻辑全部自研**——因为框架对 ToolCalling 的线程语义（流式/非流式）不够可控，自研才能做精细控制。
- **活证据**：5.1 的 ThreadLocal 权限绕过 bug，正是框架（Spring AI 流式线程切换）引入的坑——自己掌控 Agent Loop 才能第一时间定位修复。这是「不全盘交给框架」的现实理由。

**收尾升维**：不是「谁更好」，而是定位/阶段不同。快速验证想法、一次性脚本 → 直接 LangChain；把 Agent 能力作为**产品/服务交付**（多用户、可控、可观测、可扩展是刚需）→ 框架只是拼图之一，运行时工程化闭环才是主体。

**抗追问（「你不就是重新造了个 Spring AI 吗？」）**：不是。Spring AI 给的是库和抽象，我用它但不依赖其编排语义。权限模式、成本熔断、会话/记忆/技能/多租户持久化、MCP 管理、指标、SSE、多 Agent 拓扑——Spring AI 一个都没有，是我在它之上补的**运行时层**。

### 4.8 可观测性（ChatMetrics）

### 4.9 多 Agent 编排（LLM-as-Orchestrator，2026-08-16；2026-08-27 分布式化）

**定位**：不是静态工作流编排（Airflow/Temporal 的预定义 DAG），而是 **LLM 驱动的动态 Agent 编排**——harness 只提供派发原语与拓扑约束，拆不拆、拆几个、串行/并行、何时停止，全部由模型运行时实时决策（对标 OpenHarness 的 subagent 委派与团队协作）。

**编排三原语工具**：

| 工具 | 作用 |
|------|------|
| `agent` | 派发子代理：`name` + `role`（角色设定）+ `task`（LLM 生成的子任务文本）+ `wait`（true 同步等待 / false 后台并行） |
| `send_message` | 向子代理续话 / 收取后台子代理结果（RUNNING 时轮询 TaskManager 状态有界等待 `wait_seconds`） |
| `task_stop` | 终止子代理（置 STOPPED + 跨实例 Redis cancel flag） |

**子代理生命周期**（`SubagentRegistry`）：`RUNNING → COMPLETED / FAILED / STOPPED`。STOPPED 为终态，迟到的结果/失败被丢弃并记日志。状态全部持久化在 Redis Hash `harness:subagent:{userId}`，跨实例可见。

**Coordinator Mode 拓扑开关**（`uct8086.ai.orchestration.mode`）：

| 模式 | 拓扑 | 工具过滤策略 |
|------|------|--------------|
| `LOCAL` | 单 Agent | 启动期不注册编排工具（最彻底） |
| `COORDINATOR`（默认） | 星型：主 Agent 派发，子代理不能再派发 | 执行期剔除子代理的编排工具 |
| `SWARM` | 递归网状，子代理可继续派发 | 不剔除 |

**双层过滤机制**：`AgentScope.MAIN/SUBAGENT` × mode。关键约束：`buildToolCallbacks`（模型实际可调）与 `buildSystemPrompt`（模型自以为有）必须使用**同一排除集**，否则模型会尝试调用不存在的工具。

**分布式派发链路**（2026-08-27 改造，生产可用）：

```
编排者实例 A                       Redis                       Worker 实例 B
──────────────         ──────────────────────────────         ────────────────
AgentTool.doExecute
  ├─ sessionManager.createSession ───► harness_session (MySQL)
  ├─ subagentRegistry.register  ─────► harness:subagent:{userId} (Redis Hash)
  ├─ taskManager.createTask      ─────► harness:task:stream (Redis Stream msg)
  │                                       │
  │                                       ▼
  │                                  TaskManager.pollLoop (Consumer Group)
  │                                    └─ "SUBTASK" handler (AgentCoordinator)
  │                                         ├─ engine.execute(..., AgentScope.SUBAGENT)
  │                                         ├─ subagentRegistry.markCompleted
  │                                         │   ─────────────► harness:subagent:{userId}
  │                                         └─ TaskManager.updateStatus
  │                                             ─────────────► harness:task:{userId}
  │
  └─ wait=true: 轮询 taskManager.getTask 直到 COMPLETED
       └─ 读 subagentRegistry.lastResponse → 返回给 LLM
```

**触发链**（子任务从哪来 / AgentTool 在哪触发）：

```
启动期：registerTools() 按 mode 过滤注册
每轮循环：buildToolCallbacks() 把 AgentTool 包装进 ToolCallback[]
   ↓
LLM 读编排指引（PromptAssembler 注入）→ 自主决定拆分 → 输出 tool call:
   agent(name="researcher", role="负责检索", task="...", wait=true)
   ↓
Spring AI ToolCallingManager 按 name 匹配 → HarnessToolCallbackAdapter → AgentTool.doExecute()
   ↓
createSession()（独立会话）→ subagentRegistry.register(name, role, sessionId)
   → taskManager.createTask("SUBTASK", {name, role, task, sessionId})
   ↓
Redis Stream 派发到任意 worker 实例 → AgentCoordinator 的 SUBTASK handler 消费
   → engine.execute(..., AgentScope.SUBAGENT) → 子 Agent Loop（excluded=编排三件套）
   → subagentRegistry.markCompleted(state, response)
```

**「子代理」的本质**：一次带新 session id + role prompt + `AgentScope.SUBAGENT` 的 `executeInternal` 递归调用。四个特征与代码佐证：

| 特征 | 代码佐证 |
|------|---------|
| 独立会话 | `AgentTool` `createSession(userId, "subagent:"+name, true)` 新建 session，消息写独立 `harness_session`/`harness_message`，与主会话物理隔离；sessionId 经 Redis Hash 跨实例可见 |
| 角色设定 | `agent` 工具必填 `role` 参数 → payload 里随 taskId 一起传给 worker → `AgentCoordinator.SUBTASK handler` 透传给 `engine.execute(additionalContext=role)` → `PromptAssembler` 注入 system prompt |
| 独立 Agent Loop | worker 上 `AgentCoordinator` 调 `engine.execute(...)` 走与主代理完全相同的 `executeInternal`，独立 `AgentLoopResult`（自己的 turns/token 计量） |
| 能调工具 + 多轮推理 | `buildToolCallbacks` 仅剔除编排三件套，read/bash 等全可用；ToolCallingManager 循环执行至模型给出无工具调用的最终回答 |

**分布式改造前后对照**：

| 维度 | 改造前（单机版） | 改造后（分布式版） |
|------|----------------|------------------|
| 状态层 | JVM `ConcurrentHashMap` | Redis Hash `harness:subagent:{userId}` |
| 句柄 | `java.util.concurrent.Future`（不可跨进程） | `TaskManager` taskId + Redis cancel flag |
| `send_message` 等待 | `future.get(timeout)` | 轮询 `taskManager.getTask(taskId)` 状态 |
| `task_stop` 取消 | `future.cancel(true)`（本地有效） | `taskManager.cancelTask`（跨实例生效） |
| 容量 | 单进程 `ThreadPoolExecutor(2,6,queue=20)` | 所有 worker 共享 Consumer Group，弹性扩展 |
| 跨实例可用性 | ❌ 失效（其他实例找不到子代理） | ✅ 三个原语行为一致 |

**编排可观测性**（日志标志链，INFO 级即可判定）：

```
Orchestrator delegating to sub-agent 'researcher' (userId=..., sessionId=..., wait=true)  ← AgentTool 派发入口
Task enqueued: researcher (...) type=SUBTASK for user ...                                  ← TaskManager 入队
Subagent 'researcher' executing task (userId=..., sessionId=...)                            ← Worker 消费
Starting agent loop for session <子会话> (scope=SUBAGENT, excluded=[agent, send_message, task_stop])
Agent loop finished (scope=SUBAGENT): 3 turns, 2 tool calls
Sub-agent 'researcher' → COMPLETED (sessionId=...)                                          ← SubagentRegistry 状态落定
```

数据库佐证：编排发生后 `harness_session` 表多出子代理独立会话；Redis 中 `harness:subagent:{userId}` 与 `harness:task:{userId}` 都有对应条目。

**主代理流式 vs 子代理非流式（隐藏架构细节）**：两条执行路径不对等——

| 路径 | 入口 | 底层调用 | 结果返回 |
|------|------|---------|---------|
| 主代理 | `executeStream` → `executeInternalStream` | `chatClient...stream()`（`Flux`） | SSE 逐 token 推前端（打字机） |
| 子代理 | worker 上 `AgentCoordinator.SUBTASK handler` → `engine.execute` → `executeInternal` | `chatClient...call()`（同步） | `AgentLoopResult` 一次性返回，写回 Redis Hash |

- 主循环 `executeInternalStream` 里 `buildSystemPrompt(..., null, ...)` 的 `additionalContext` 恒为 **null**——角色注入只发生在子代理的 `executeInternal` 路径（worker 从 payload 取 role 透传给 `engine.execute`）。
- 设计合理性：子代理是**工具内部实现**，其结果只需回传给主代理做下一步决策（非流式更简单可控）；真正需要「边生成边展示」的只有面向用户的主循环（流式 SSE）。

**分布式化的工程价值**：改造前 `SubagentRegistry` 是内存 Map、`task_stop` 用本地 `Future.cancel`——这些在单机部署下能工作，但**水平扩展后跨实例失效**（编排者实例 A 派发的子代理，实例 B 上的 `send_message` 找不到）。改造后三个原语全部走 Redis（Hash 状态 + Stream 派发 + cancel flag），编排者与 worker 可不是同一个实例，行为完全一致。单机实现的完整留档见 [orchestration-single-node-legacy.md](./orchestration-single-node-legacy.md)；分布式实现详见 [orchestration-patterns.md](./orchestration-patterns.md) §3。

## 五、关键调整与踩坑记录（面试亮点）

> 这些是「从开发态到接近生产级」的演进过程，最能体现工程能力和对细节的把控。

### 5.1 🔴 ThreadLocal 权限绕过（最高价值修复）

- **问题**：工具回调上下文原用 `static ThreadLocal<ToolExecutionContext>`。Spring AI 2.0 **非流式** `.call()` 路径工具执行同线程，碰巧可用；但**流式** `.stream()` 路径会把工具执行切到 `Schedulers.boundedElastic()` 线程池，ThreadLocal 取不到 context → 触发 `PermissionMode.AUTO` 兜底 → **危险命令（bash）确定性绕过权限检查**。
- **修复**：弃用 ThreadLocal，把 context 改为**构造注入的实例字段**。因为 `buildToolCallbacks()` 每次请求都 new 一批 adapter，context 跟着实例走、与执行线程无关。
- **价值**：为切换流式模式扫清一个「切换即触发」的安全定时炸弹。

### 5.2 权限模式从全局可变 → 请求级

- **问题**：权限模式是单例 `volatile` 字段，`AgentEngine` 每次请求 `setMode`、Controller 也改同一变量，多用户并发互相覆盖，前端设置被配置文件默认值「覆盖回去」。
- **修复**：改为 `AtomicReference<PermissionMode> defaultMode`。配置作**初始默认值**，运行时设置**优先**；请求只 `getMode()` 读、不再写全局状态，权限模式通过 `ToolExecutionContext` 传递。

### 5.3 状态外置：从单机内存/文件 → 共享存储

| 组件 | 改造前 | 改造后 |
|------|--------|--------|
| CostTracker | 内存 `LongAdder`（重启清零） | MySQL `cost_usage` 表 + SQL SUM |
| 记忆 | 本地文件 `MEMORY.md` | MySQL `harness_memory` + 向量索引 |
| 用户技能 | 本地文件 | MySQL `harness_skill` |
| TaskManager | 内存 Map（重启丢任务） | Redis Stream + 消费组（at-least-once 跨实例分发） |
| SubagentRegistry | JVM `ConcurrentHashMap` + `Future`（跨实例失效） | Redis Hash `harness:subagent:{userId}` + TaskManager taskId（2026-08-27 分布式化） |

- **决策依据**：成本/记忆是「长期持久化 + 可查询追溯」业务数据 → 放 MySQL；任务执行体是 JVM `Callable` 无法序列化进 DB → 改「任务描述（type+payload）」入 Redis Stream，消费者按 `taskType` 分发到注册的 `TaskHandler`；子代理状态需要跨实例可读但不必长期持久化 → Redis Hash（TTL 24h），与 TaskManager 同套 Redis 基础设施复用。
- **演进式债务**：SubagentRegistry 最初是和编排三原语一起加的内存实现，沿用单机心智模型——前期生产化改造（CostTracker/TaskManager 等）已把状态外置做了，但当时编排骨子还没有，所以这次改造是把"叠加编排时漏掉的一步"补上。

### 5.4 并发安全修复清单（11 项）

- `CostTracker` 非原子累加 → `LongAdder`/`DoubleAdder`（后外置 MySQL）。
- `SessionManager.createSession` 竞态 + count 全扫 → UUID。
- 三处文件无锁写（Memory/MCP/Skill）→ `synchronized` + 原子写（`.tmp` + `ATOMIC_MOVE`）。
- MCP 每次 `new ObjectMapper()` → 共享 `static final` 实例。
- `TaskManager` 无界线程池 → 有界 `ThreadPoolExecutor(4,16,LinkedBlockingQueue(1000))` + daemon。
- `BashTool` 输出无上限 → 限制 1MB 截断。
- `HarnessProperties.workingDirectory` 静态初始化 → null + getter 懒解析（容器化友好）。
- DEBUG 日志泄漏 prompt → INFO。
- **SubagentRegistry 内存化 → Redis Hash**（2026-08-27）：JVM `ConcurrentHashMap` 跨实例失效，改为 Redis Hash 按 `userId` 命名空间化，三个编排原语（`agent` / `send_message` / `task_stop`）跨实例行为一致。详见 4.9 节「分布式改造前后对照」。

### 5.5 Chat 接入方式的演进（对外桥接）

- 早期用 username/password token-exchange（OkHttp 拦截器自动登录），后弃用改 PAT 直连。
- 采用 **OpenAI 兼容协议** 桥接：本地起一个轻量桥接服务（TypeScript/Express），把 OpenAI 格式请求转发给实际模型后端，Java 侧用 `spring.ai.openai` 直连 `http://localhost:3000/v1`。
- **关键坑**（已记录并解决）：
  - Spring AI 2.0 用 OpenAI 官方 Java SDK，`base-url` **必须含 `/v1`**（SDK 直接拼 `/chat/completions`），否则 404。
  - 桥接端点默认要改成**非流式**（`body.stream === true`），否则 Spring AI 不带 stream 参数会收到 SSE 解析失败。
  - `messagesToPrompt` 只传最后一个 user message（避免 agentic system prompt 被误执行）。
  - Windows 下 spawn 需 `shell: true`（不解析 `.cmd`）。
  - 运行时覆盖 model 用 `prompt.options(OpenAiChatOptions.builder().model(m))`，传 **Builder** 而非实例（`options()` 接受 `ChatOptions.Builder<?>`）。
  - 流式 token 统计：DeepSeek 流式默认不返回 usage，需 `stream_options.include_usage=true`，否则用「字符数/2」启发式估算兜底。

### 5.6 SSE 流式输出

- `AgentEngine.executeStream` 用 `SseEmitter` 逐 token 推送（`token`/`tool`/`done`/`error` 事件），前端打字机效果。
- **流式基于 Reactor `Flux`**：`chatClient.prompt()...stream().chatClientResponse()` 返回 `Flux<ChatClientResponse>`——LLM 输出不是一次性值，而是逐 token 的**增量序列**。代码用 `doOnNext`（每来一个增量：文本 token 追加 + 推 SSE / 工具调用计数）与 `doOnComplete`（流结束：持久化 + 记账 + done 事件）订阅它。
- **`Flux` 的连带效应——线程模型切换（呼应 5.1）**：`.call()` 同步阻塞、工具执行在当前线程；`.stream()` 走响应式，底层把工具执行切到 reactor 线程池（`boundedElastic`）。这正是 5.1 ThreadLocal 权限绕过 bug 的根因——Flux 不只是「怎么收结果」，还决定了「代码跑在哪个线程」。
- 有界线程池 `streamExecutor(2,8,LinkedBlockingQueue(50))` 避免线程爆炸，队列满拒绝并记日志。
- SSE 端点 `permitAll` + controller 层 `CurrentUser.requireId()` 手动鉴权（绕开 STATELESS 下 async dispatch 空 SecurityContext 的坑）。

## 八、面试可能被追问的点（自测清单）

- **为什么用 Redis opaque token 而不是 JWT？** 即时吊销、无状态跨节点、实现简单；代价是每次请求要查 Redis。
- **记忆和知识库共用向量库，怎么隔离？** metadata `type` + `userId` 字段，代码层过滤，避免 DB filter 表达式的 provider 差异。
- **成本熔断怎么做的？** 请求前 `assertQuota` 查 SQL SUM 总成本，超限抛异常 + Redis 熔断标志 + 多级告警。
- **ThreadLocal 那个 bug 的根因？** Spring AI 流式路径把工具执行切到 reactor 线程池，ThreadLocal 跨线程失效，触发权限兜底。
- **为什么 Embedding 用 Ollama 不用 DeepSeek？** DeepSeek 无 Embedding API；Ollama `bge-m3` 本地免费、1024 维中文效果好、数据不出内网。
- **为什么任务队列用 Redis Stream 不用 MySQL？** 任务体是 JVM Callable 无法序列化进 DB，改「描述 + handler 注册」模式，Redis Stream 消费组实现 at-least-once 跨实例分发。
- **编排是静态工作流还是动态的？** LLM 驱动的动态 Agent 编排：harness 只提供 `agent`/`send_message`/`task_stop` 三原语 + LOCAL/COORDINATOR/SWARM 拓扑约束，拆分决策 100% 在模型运行时。
- **子代理和主代理的实现差异？** 同一个 `executeInternal` 递归，仅两个参数不同：新 session id + `AgentScope.SUBAGENT`（剔除编排工具，保证星型拓扑不失控）。worker 上跑，状态回写 Redis Hash。
- **怎么判断编排真的发生了？** 日志标志链 `Orchestrator delegating` → `Task enqueued ... type=SUBTASK` → `Subagent '...' executing task` → `Starting agent loop (scope=SUBAGENT)` → `Sub-agent → COMPLETED`，加上 `harness_session` 多出子代理独立会话、Redis 中 `harness:subagent:{userId}` 与 `harness:task:{userId}` 都有对应条目。
- **分布式部署下子代理怎么跨实例工作？** 三个原语全部走 Redis：`agent` 调 `TaskManager.createTask("SUBTASK", ...)` 把子任务丢进 Redis Stream，任意 worker 实例消费；子代理状态在 Redis Hash `harness:subagent:{userId}`；`send_message` 轮询 `TaskManager.getTask` 而非本地 `Future`；`task_stop` 用 Redis cancel flag 跨实例中断 worker。这样编排者实例与 worker 实例可不同，水平扩展时三个原语行为完全一致。
- **为什么不用 LangChain / AgentScope？** 它们是编排框架（回答「Agent 怎么写」），我是运行时基础设施（回答「Agent 怎么跑、怎么管、怎么不失控」）——权限/成本/多租户/记忆闭环/可观测这些工程化能力正是框架盲区。详见 4.10。

## 九、口语版面试叙述（可直接照说）

> 面试时「讲项目」的口语化稿子，按自然讲述顺序编排，避免背书感。每条都对应前面章节的展开，可据面试官反应伸缩。

### 9.1 项目一句话介绍

> 我做的是一个基于 Spring AI 2.0 的 **Agent 运行时基础设施**，Java 21 + Spring Boot 4.0。它不是一个套壳的聊天接口，而是一套可插拔的 Agent 运行时框架，提供了完整的闭环能力：多 Agent 任务编排、会话管理、技能系统、用户级记忆自动固化、知识库 RAG（pgvector 向量检索）、MCP 协议接入、四级权限管控、用量管理和成本熔断、多租户隔离、SSE 流式输出，还有 Prometheus 可观测性。

### 9.2 Agent Loop 核心流程

> 我先讲一下最核心的 Agent Loop 是怎么跑的。整个流程是：
>
> 第一步，做**成本熔断检查**——请求进来先查一下这个用户的累计成本，如果超过硬上限，直接拒绝，写一个 Redis 熔断标志，前端提示超预算；没超才继续。
>
> 第二步，**创建或恢复会话**，用 MySQL 持久化，Redis 做缓存。
>
> 第三步，**组装 System Prompt**，这里面会注入三类东西：系统技能和用户技能（每条截断到 4000 字符控制 token 预算）、相关的记忆（向量检索取最相关的 5 条）、还有 RAG 检索到的知识库文档（取前 3 条）。
>
> 第四步，**加载历史消息**，取最近的 N 条，这个 N 是可配置的，默认 10。这里有个细节——历史消息是在持久化当前这轮用户消息**之前**加载的，所以注入的历史不包含当前这轮，当前这轮单独追加，避免重复。
>
> 第五步，**构建工具回调**，把内置工具（bash、文件读写这些）和用户配的 MCP 工具注册进去。
>
> 第六步，**启动 ChatClient 加上一个自定义的 Advisor 循环**——模型请求工具 → 工具执行管线 → 结果回传 → 直到模型不再调用工具。
>
> 最后第七步，**持久化消息、记账、记录指标**。

### 9.3 会话怎么存的

> 会话这块我用的是 **MySQL 持久化 + Redis 三级缓存**的组合。
>
> MySQL 是唯一的真相源，存 `harness_session` 和 `harness_message`，重启不丢。Redis 上建了三级缓存，全是 MySQL 的只读副本：第一级是一个 ZSET 有序索引，按更新时间排序，存这个用户的全部会话 id；第二级是每个会话的元信息缓存；第三级是每个会话的消息列表。
>
> 查询的时候，先看 ZSET 这个 key 存不存在——不存在说明缓存冷启动或者 Redis 挂了，就整页降级去查 MySQL 分页；存在的话，从 ZSET 里倒序取出会话 id，再批量去查元信息缓存。这里有个细节，因为 ZSET 和元信息的 TTL 不一样，会出现「索引还在、明细已经过期」的中间态，所以个别缺失的条目要单独回源数据库补，而不是一缺就整页降级。
>
> 核心思路就是：**缓存是加速层，MySQL 是保底层，Redis 挂了系统照样能用，只是慢一点**。

### 9.4 流式输出怎么实现的

> 流式输出这块，我用的是 SSE 加 Reactor 的 Flux。调用 `.stream()` 拿到的是一个 `Flux<ChatClientResponse>`，它不是一个一次性返回值，而是模型逐 token 生成的增量序列。
>
> 我对这个流做了两个订阅：每来一个增量，如果是文本 token 就追加到全文再推给前端，如果是工具调用就计数并通知前端；等流结束的时候，再做收尾——把完整回复持久化、记账、发 done 事件。
>
> 这里顺带有个很关键的点，也是我之前踩过坑的地方：`.call()` 和 `.stream()` 的线程模型不一样，`.stream()` 走响应式，会把工具执行切到 reactor 的线程池里。我之前用一个 ThreadLocal 存工具执行上下文，流式模式下跨线程就取不到了，导致危险命令的权限检查被绕过。这个坑让我意识到用 Flux 不光要理解「怎么收结果」，还要理解「代码跑在哪个线程」。

### 9.5 多 Agent 编排怎么做的

> 编排这块我实现的是 **LLM 驱动的动态 Agent 编排**，不是那种预先画好流程图的静态工作流。harness 只提供三个工具原语：`agent` 派发子代理、`send_message` 给子代理续话收结果、`task_stop` 终止子代理。拆不拆、拆几个、并行还是串行，全由模型在运行时自己决定。
>
> 这里有个隐藏的架构细节：主代理和子代理的返回路径是不对等的。主代理走流式，SSE 逐 token 推给前端；子代理走非流式，一次性返回结果给主代理。原因也简单——子代理本质上是工具的内部实现，它的结果只需要回传给主代理做下一步决策，不需要边生成边展示；只有面向用户的主循环才需要打字机效果。
>
> 还有一个值得说的点是分布式化。最早编排这套是按单机做的：`SubagentRegistry` 是 JVM 内存 Map，`task_stop` 用本地 `Future.cancel(true)`，子代理在进程内线程池上跑。前期做生产化改造时把 CostTracker、TaskManager 这些状态都外置到 Redis/MySQL 了，但当时编排骨子还没有，所以这一块漏了。后来加编排时沿用了单机心智模型，结果水平扩展时三个原语跨实例都失效——实例 A 派发的子代理，实例 B 上的 `send_message` 找不到。
>
> 我后来把这一块也改成了分布式：状态层从 `ConcurrentHashMap` 换成 Redis Hash `harness:subagent:{userId}`；`agent` 工具不再开本地线程，而是调 `TaskManager.createTask("SUBTASK", ...)` 把子任务丢进 Redis Stream，任意 worker 实例消费组里的成员都能捡起来跑；`send_message` 不再 `future.get` 而是 500ms 一次轮询 `TaskManager.getTask` 看 worker 报没报 COMPLETED；`task_stop` 改成调 `TaskManager.cancelTask`，靠 Redis cancel flag 跨实例中断 worker。改造之后编排者实例和 worker 实例可以不是同一个，三个原语在多实例部署下行为完全一致。
>
> 这次改造的反思是：**单机心智模型 + 阶段性交付 = 隐性单机约束**。新加子系统时应该回头做一次生产化 review，把新加的部分也纳入生产标准——这一步漏了，是工程演进式的盲区。识别它本身就是工程成熟度的体现。
